# Discord login and server authorization

Configure `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_REDIRECT_URI` and `AUTH_SECRET` (at least 32 random characters, identical across BE replicas) in the root `.env`, then restart BE. The redirect URI is a single server-configured allowlisted value and must exactly match the Discord Developer Portal OAuth redirect registration and the FE callback URL, for example `http://localhost:3002/` for the default Vite dev server. HTTPS is required in production (`NODE_ENV=production` marks the state cookie Secure). Request only `identify guilds`; user.email is null because email is not requested.

`DISCORD_BOT_TOKEN` logs in the Bot and does not configure Web OAuth. The authorize endpoint returns 503 with the names of missing or invalid OAuth settings, without their values. Other unexpected server errors remain hidden. FE displays this message when the login button fails. This is a configuration failure before redirecting to Discord; it does not require disabling the AuthGate or guild authorization. Obtain the Client ID and Client Secret from the application's OAuth2 settings and register the exact FE redirect URI there. Generate `AUTH_SECRET` locally (for example with `openssl rand -hex 32`); do not paste credentials into chat or commit `.env`.

FE and BE must be on the same site for the SameSite=Lax browser state cookie: use the Vite /api proxy locally or a same-origin /api reverse proxy in production. Alternatively `VITE_API_ORIGIN` supports a same-site BE hostname with `CORS_ORIGINS` set to the exact FE origin. Set CORS_ORIGINS explicitly in deployed environments. A cross-site FE/BE deployment requires an intentional cookie-policy change; it is not enabled by this flow.

1. GET `/api/v1/auth/authorize` sets a HttpOnly browser state cookie and returns Discord's authorization URL.
2. Discord redirects to FE with code and state; POST `/api/v1/auth/login` sends both with cookie credentials. State must match the browser-bound signature, expiry and unconsumed database nonce. It is consumed before code exchange; failed login restarts at authorize. The redirect URI cannot be overridden by a browser.
3. Login returns `{accessToken,tokenType:'Bearer',expiresAt,user:{id,name,email,avatarUrl,discordUserId}}` and a persistent `ggaddak_session` cookie. Its random 256-bit credential is HttpOnly, SameSite=Lax, scoped to `/api/v1/auth`, Secure in production, and expires at the fixed seven-day server session deadline. Only its SHA-256 hash is stored in AuthSession. The cookie value is never returned in JSON.
4. FE boots and reconnects with POST `/api/v1/auth/session`, using cookie credentials and an Origin matching the configured callback origin. This returns a short-lived JWT, user and authorized guilds. Live Gateway coverage permits reuse of verified guild memberships; uncovered or invalidated permissions are rechecked with Discord. The access JWT remains in memory. A session is never extended beyond its initial seven days. Missing/expired/revoked cookies return 401; a disallowed or missing Origin returns 403. Transient provider/network failures retain the session and FE blocks data until retry succeeds.
5. POST `/api/v1/auth/token` renews only the access JWT from the browser cookie and matching Origin. It returns `{accessToken,tokenType,expiresAt,userId}` and never contacts Discord. Browser FE uses this when an actual API request encounters an expired JWT; there is no periodic session/permission polling. `userId` prevents a missed browser account-change signal from pairing another user's token with old UI data. The Bearer-JWT POST `/auth/refresh` likewise only renews JWTs. Permission revalidation has separate DB leases/versioning and coalesces concurrent requests. Rotated Discord credentials are persisted before fetching guilds so a transient guild outage does not discard them. Confirmed invalid_grant or identity/guild API 401 revokes the affected session; upstream client configuration errors and generic failures do not.
6. POST `/auth/logout` accepts the persistent cookie with matching Origin, including when the access JWT has expired. It deletes only that session and clears its cookie. Legacy bearer-only logout is retained. FE clears memory and query caches, broadcasts logout to the same browser's other tabs, and leaves other browsers/devices independent. Login/user changes are broadcast too; an old user's in-flight request cannot be replayed under a new user. The remembered guild is stored per user and restored only if still authorized.
7. JWT continues to validate signature, issuer, audience, expiry and persisted session. Membership proofs are invalidated by Gateway changes rather than a 15-minute cache expiry. Data requests revalidate permissions whenever event coverage is absent or continuity is uncertain. AUTH_SECRET rotation invalidates old JWTs and encrypted provider credentials; users sign in again. Existing pre-migration sessions have no browser cookie and require one new login to gain restoration.

`@Security('jwt')` supplies `request.user` as `{userId,sessionId}`. `AuthService.requireGuild(principal,guildId,manage=false)` is mandatory before server queries; `manage=true` additionally requires guild owner or MANAGE_GUILD. `requireDecision(principal,id,guildId?)` verifies the stored Decision guild and optional selected-guild match before direct-ID reads or writes. TSOA controllers and security resolution use app-local services, so distinct servers cannot share authorization state or repositories. Successor endpoints must use these methods; bearer verification alone does not authorize a guild.

Migration `202610120004_discord_auth` is additive. It creates User/Guild/Membership/AuthSession/OAuthState, seeds historical Guild IDs and does not alter Decision records or grant historical memberships. Generate the Prisma client and apply migrations only to an explicitly selected/backed-up DB. No production database was migrated during ticket implementation. See [ERD](../../docs/diagrams/v1-data-model.md).

The Bot uses `BOT_SERVICE_TOKEN` as a bearer token for internal monitoring, discussion analysis, candidate-history and guild-access event endpoints. Both GET and POST `/api/feedbacks` require this service credential. User JWTs cannot access global legacy feedback; server-scoped web feedback remains pending.

## Event-driven guild authorization

Enable `DISCORD_GUILD_MEMBERS_INTENT=true` for Bot and enable Server Members Intent in Discord Developer Portal before starting it. The default is false: without the intent, membership event coverage is never claimed and protected requests revalidate with OAuth. Bot installation and user membership remain separate: removing the Bot does not hide saved decisions from users still in that guild.

The authenticated `/api/v1/internal/guild-access/events` stream invalidates individual memberships on leave/kick/ban and invalidates management proofs on member role, role permission or ownership changes. Rejoin events require fresh OAuth confirmation before granting access. Guild unavailable is distinct from actual Bot removal. Ordered event sequences, retained delivery records and server-side revision checks prevent retries or late OAuth snapshots from restoring revoked permissions.

Bot sends a local connection heartbeat every ten seconds, without Discord REST requests. Its 35-second lease proves only delivery liveness. It does not schedule a permissions lookup. After disconnects, sequence gaps, receiver restarts or lease expiry, actual data requests revalidate instead of trusting old proofs. Gateway Resume drains missed events before renewing trust; a new Identify/reset invalidates all previous proofs. The current producer is a single Discord client; a second live producer is refused until the first disconnects or its lease expires.

Permission denial uses v1 code `GUILD_ACCESS_DENIED`; provider/verification outages use `GUILD_ACCESS_UNAVAILABLE`. FE restores scope and clears affected data after these errors, without automatically replaying a rejected mutation. Other provider errors such as an embedding outage do not trigger permission-recovery loops. See [operations](../../docs/operations/guild-access.md).

Migration `202611030001_guild_access_events` is additive and defaults old membership proofs to unverified. It adds authorization observation metadata and does not rewrite Decision Records. Apply it only to a selected backed-up database. Automated checks use disposable databases; the operating database and Discord Portal are not changed by implementation tests.

Public HTTP test helpers: `test-support/auth.ts` provides `fakeAuthOptions()` with an injectable fake Discord adapter and `loginAsTestUser(baseUrl)` obtains a real application JWT through authorize/login. Tests use disposable DBs, never real Discord credentials.

Verified official sources (2026-10-12): [Discord OAuth2](https://docs.discord.com/developers/topics/oauth2) specifies form-encoded code/refresh exchanges, redirect URI, identify/guilds scopes and request-bound state; [Discord User Resource](https://docs.discord.com/developers/resources/user) specifies current-user and user-guild endpoints. HTTP adapter uses API v10.

Migration `202610160001_browser_session` adds nullable browser-token hash, refresh owner/lease and version fields without changing existing Decision rows. Local application backed up the active SQLite DB and preserved all 326 Decision rows. See [agreed policy and verification](../../docs/model/web-session.md).
