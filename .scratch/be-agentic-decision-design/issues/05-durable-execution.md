## Question

워크플로우 상태와 논리 그래프를 언제 무엇으로 저장하고, 중간 실패 뒤 어떤 단계에서 재개할까? 현재 요청 ID·lease·owner fencing·후보 멱등성·최종 원자 저장을 유지하면서 단계 checkpoint, 수정 반복, 전달 재시도, 명시적 재분석을 구분할 계약을 정한다.

실패를 정상 무결정으로 처리하지 않는 규칙, 그래프와 후보의 원자성, 검수·편집 후 분석 그래프의 유효성 및 버전, 기존 aggregate와 호환하는 최소 저장·API 경계를 결정한다. 이번에는 DB나 API를 수정하지 않는다.

## Answer

### 저장 단위와 재개

BE DB가 요청 입력·설정과 세션별 단계 결과·진행·예산의 권위다. 원래 요청을 재개할 수 있도록 입력 대화, 분할된 세션, 적용 설정을 고정한다. 같은 요청 ID에 다른 입력·설정을 끼워 넣어 재사용하지 않는다. 의도적인 입력·설정 변경 및 재분석은 새 요청 ID로 구분한다.

완료한 추출·검증·수정 단계 결과를 저장하고 재개 시 재사용한다. 추출은 끝났지만 의미 검증의 통신이 실패하면 저장된 추출 결과부터 검증을 이어간다. 그래프 임시 참조와 BE 발급 문자열 ID 매핑도 저장해 재개하면서 임의로 바꾸지 않는다.

AI 응답 수신과 DB checkpoint 저장 사이에 프로세스가 죽으면 저장되지 않은 호출 결과를 재사용할 수 없다. 외부 AI 호출 자체의 exactly-once를 보장하는 계약은 아니다. 단계 시도·소비 예산을 추적하고, 중복 후보·그래프 공개는 요청 멱등성과 원자 반영으로 막는다. 구체적인 checkpoint 테이블·단계 시도 ledger는 이 의미를 유지하는 구현 명세에서 정한다.

### 요청별 원자 공개

요청에 여러 세션이 있으면 모든 세션이 검증 통과 또는 검증된 후보 없음으로 성공해야 공개한다. 중간 그래프·후보 결과는 재개용으로 저장하지만 검수 큐, 카드 목록, 검색, 완료 그래프 조회에 공개하지 않는다.

최종적으로 분석 그래프·실제 후보 생성 또는 기존 후보 연결·요청 완료 결과를 같은 transaction으로 반영한다. 완료 요청의 재전송은 저장된 결과를 반환하며 중복 후보나 별도 그래프를 추가하지 않는다. 후보가 없어도 맥락 그래프를 보존하고 정상 완료할 수 있다.

세션 중 하나라도 최종 실패하면 요청을 성공이나 정상 무결정으로 처리하지 않는다. 완료한 다른 세션의 중간 결과는 복구·진단용으로 유지하고 부분 공개하지 않는다. 완료한 스캔의 acknowledgement와 Channel Checkpoint 규칙은 ADR-0020을 유지한다.

### 수정·시간·통신 재시도

동일 요청·세션의 수정 예산은 최대 한 번이며 재개·전달 재시도로 초기화하지 않는다. 논리적 AI 단계는 최대 4회다. 동일 단계의 일시적 통신 재시도는 수정이 아니며 별도 시도로 기록하고 기존 bounded delivery 정책을 따른다.

세션 시간 상한 180초는 재시도 대기 시간을 제외한 누적 활성 실행 시간이다. 이미 소비한 시간을 저장하고 재개 시 남은 예산만 사용한다. 호출당 최대 45초이며 남은 전체 예산을 초과하지 않는다. 실행·코드 검사·통신 실패에 사용한 시간도 소비 시간에 포함한다. 결과를 받지 못한 프로세스 중단을 이유로 과거 실행 시간을 없었던 것으로 취급하지 않도록 시도 시작·deadline 정보를 보존한다.

수정 이후에도 검증 오류가 남거나 수정·시간 예산이 소진되면 terminal failure로 보존한다. 같은 요청을 재전송하여 terminal failure를 다시 분석하거나 예산을 늘리지 않는다. 일시적 통신 실패는 남은 예산 안에서만 재개 가능하다. 별도 수동 재분석은 새 요청이며 이전 분석·실패와 이력으로 연결한다. 기존 retained failure retry API에서 ‘전달 재시도’와 ‘새 분석’의 구별이 필요한 부분은 구현 명세·기존 AI 티켓 조정에 반영한다.

### 소유권과 취소

기존 request lease·heartbeat·owner fencing을 단계 저장과 최종 반영까지 유지한다. 소유권을 잃은 worker는 새 AI 호출·후속 단계·저장을 중단하고 이전 소유자의 결과를 반영하지 않는다. 가능한 경우 진행 중 호출도 취소한다. late response가 도착해도 최신 소유권 없이 저장하지 않는다.

완료 checkpoint부터 새 소유자가 남은 예산으로 재개하며 동일 요청의 동시 실행·중복 공개를 차단한다. 별도 사용자 취소 API 추가는 이번 합의에 포함하지 않는다.

### 인간 검수 이후의 그래프

완료 AI 그래프는 당시 입력·설정·결과의 분석 snapshot으로 보존한다. 사람이 후보를 편집·확정·보류·폐기하거나 Supersede하더라도 과거 AI 노드·관계 내용을 덮어쓰지 않는다. 실제 카드 ID 및 인간 변경 버전과 연결해서 분석 당시 결과와 현재 카드가 다를 수 있음을 구별한다.

분석상 철회·충돌 관계를 서비스의 Rejected/Superseded 상태 변경으로 취급하지 않는다. 기존 expectedVersion과 인간 검수의 원자 상태 변경을 유지한다. 원본 분석 그래프를 최신 카드 모델과 섞어 최신 그래프인 것처럼 제공하지 않는다.

### 조회 계약

기존 카드 목록·상세 API는 유지하고 그래프 조회를 분리한다. 완료 그래프는 분석 요청 기준으로 조회하며 Decision Candidate 노드에 실제 카드 ID를 연결한다. 카드에서 연관된 분석 요청을 찾아 그래프로 이동할 수 있도록 관계를 제공한다. 같은 카드가 여러 분석과 연결될 수 있으므로 단일 graphId로 관계를 덮어쓰지 않는다.

그래프 조회는 해당 guild에 대한 사용자 접근 권한을 검증한다. 요청 ID나 카드 ID를 알더라도 다른 서버의 분석 데이터를 볼 수 없다. 중간·실패 분석을 완료 그래프로 제공하지 않는다. 실패 상태·원인은 실패 조회 경로에서 다루며 구체적인 진단 API는 구현 명세에서 정한다.

### 다음 결정

단계별 토큰·비용·지연, 품질 수용 기준, 모델 선택, 실제 평가 도구 및 기존 AI 티켓의 유지·수정·대체는 평가·인계 티켓에서 정한다. 이 답변은 설계 합의이며 DB·앱 코드·API 구현은 변경하지 않았다.
