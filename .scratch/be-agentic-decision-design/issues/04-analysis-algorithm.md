## Question

어떤 단계에서 LLM을 호출하고 어떤 검사를 코드가 수행할까? 후보 추출·관계 구성·대화 내부 충돌 탐지·검증·수정을 단일 호출 또는 분리 단계로 구성할지, 단계별 입력·출력·분기·실패 시 결과·종료 조건을 결정한다.

검증 실패의 재생성 대상과 최대 반복·호출·토큰·시간 예산, 부분 성공과 무결정의 구별, 동시 실행 범위, 공급자 추상화 및 orchestration 구현 선택을 정한다. Governance Score와 검증 결과의 목적을 구별하고, 연구 문서의 점수 임계치나 최대 3회 반복을 근거 없이 채택하지 않는다.

## Answer

### 실행 책임과 입력

BE Service가 고정 workflow의 단계·분기·예산·종료를 제어한다. Adapter는 단계별 AI 호출과 공급자별 구조화 출력 처리를 담당한다. 기존 TypeScript 구조를 사용하며 동적 supervisor, 별도 노드/관계 추출기, LangGraph는 도입하지 않는다.

이번 세션의 대화만 분석한다. 과거 Decision Record retrieval이나 기존 pipeline의 외부 피드백을 분석 근거로 주입하는 것은 이 범위에 포함하지 않는다. 대화에 포함되지 않은 배경·이유·합의를 추가하지 않는다. 그래프·후보 의미는 해결된 선행 티켓을 따른다.

### 단계와 분기

1. **추출:** 입력 대화에서 후보·그래프 노드·관계·대화 관측·순서 있는 이력을 함께 생성한다. 연결에 필요한 임시 참조를 사용하고 BE가 최종 문자열 ID를 발급한다. 임시 참조와 최종 ID의 저장 경계는 후속 저장 티켓에서 결정한다.
2. **코드 구조 검사:** 응답 형태·텍스트·노드/관계 종류·ID 유일성·끝점 존재·허용 연결을 검사한다. 구조 검사를 통과하기 전 의미 검증·검수 제출로 진행하지 않는다.
3. **AI 의미 검증:** 입력 대화와 추출 결과를 별도 호출에 함께 제공한다. 누락 후보, 입력에 없는 내용·근거, 잘못된 합의·철회·대안 관측, 관계 오류를 검사한다. 문제 목록은 수정할 내용과 그 이유를 전달한다. 원문 인용이나 메시지별 출처 연결은 검증의 필수 조건이 아니다.
4. **조건부 수정:** 구조 또는 의미 오류가 있을 때만 원문·현재 결과·오류 피드백으로 결과를 수정한다. 한 세션에 수정은 최대 한 번이며 구조와 의미 검증이 같은 수정 예산을 공유한다.
5. **재검사:** 수정 결과는 코드 구조 검사부터 다시 거쳐 AI 의미 검증을 통과해야 한다. 허용 예산 안에서 모두 통과하면 제출 가능한 결과로 완료한다.

정상 경로는 추출·의미 검증 2회 AI 호출이다. 의미 수정 경로는 추출·의미 검증·수정·의미 재검증 최대 4회다. 첫 구조 검사에서 실패한 경우 추출·수정·의미 검증 경로로 최대 3회다. 구조 보정에서 수정 예산을 이미 사용한 뒤 의미 오류가 발견되면 추가로 수정하지 않는다.

후보가 없는 결과도 의미 검증한다. 정상이라면 후보 없음으로 완료하되 문제·질문 등의 그래프 맥락을 보존한다. 의미 검증 호출 자체가 실패한 결과를 후보 없음으로 처리하지 않는다.

### 검증 오류와 실제 대화 모순

실제 대화에 나온 상충 합의·철회·순환 의존은 검증 실패가 아니다. 분석이 그 사실을 올바르게 표현하면 문제 표시와 함께 제출한다. 입력에 없는 모순을 생성하거나 실제 모순을 숨기면 검증 오류다. AI가 임의로 관계나 대안을 삭제해 합의가 있는 것처럼 만들지 않는다.

수정 뒤에도 구조·의미 오류가 남으면 전체 분석을 실패로 보존한다. 검증되지 않은 일부 후보를 조용히 제출하지 않는다. 여러 세션을 포함한 요청의 저장 원자성과 재개 범위는 후속 저장 티켓에서 결정한다.

### 예산과 종료

- 초기 시간 상한은 AI 호출당 45초, 세션 workflow 전체 180초다. 코드 검사·수정·재검증도 세션 deadline 안에 수행한다. 호출은 남은 전체 시간보다 오래 기다리지 않는다.
- 내용 수정은 최대 한 번, 논리적 AI 단계 호출은 최대 4회다. 공급자 통신 재시도는 별도 동작이며 호출 수·토큰·시간을 따로 기록하고 기존 전달 재시도 정책과 연결한다. 전달 재시도·checkpoint·owner fencing의 구체적인 예산 범위는 저장 티켓에서 정한다.
- 검증 통과 또는 검증된 후보 없음이면 성공 종료한다. 오류 지속·수정 예산 소진·시간 상한 초과이면 실패 종료한다. 같은 오류가 수정 뒤 반복되면 추가 루프를 돌리지 않는다.
- 토큰 사용량을 단계별 기록하고 입력·출력 한도의 구체값은 평가 티켓에서 결정한다. 한도 초과를 입력의 조용한 절단이나 잘린 출력의 정상 완료로 처리하지 않는다.

위 숫자는 초기 운영 예산에 대한 사용자 합의다. 모델 품질·비용·지연을 검증한 최적값이라는 뜻은 아니며 평가 결과로 조정할 수 있다.

### 동시성과 점수

같은 채널의 분석은 기존 순차 실행을 유지한다. 한 세션의 추출·검증·수정도 순차 실행하며 worker fan-out을 도입하지 않는다. 통신 실패 재전송은 기존 요청 ID를 유지하고 내용 수정·명시적 재분석과 구분한다. 다른 채널의 기존 실행 정책은 유지한다.

Governance Score는 현재 규칙 기반 참고 지표이며 의미 검증 결과나 합의 확률과 동일하지 않다. 점수로 검증을 우회하거나 자동 확정하지 않는다. 별도 합의 점수 임계치 0.85 등의 검증되지 않은 기준은 채택하지 않는다.

### 다음 결정

단계 저장·재개, 요청 전체의 원자성, 전달 재시도와 예산 재설정 범위, 소유권 상실·취소, 검수 후 그래프의 유효성은 저장·재시도 경계 티켓에서 결정한다. 모델·토큰 한도·품질 수용 기준과 기존 AI 티켓 조정은 평가 티켓에서 결정한다. 앱 코드와 DB는 아직 변경하지 않았다.
