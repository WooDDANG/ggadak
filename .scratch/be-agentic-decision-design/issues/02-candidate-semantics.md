## Question

합의되지 않은 제안도 검수 후보로 제출할 때, 입력 대화의 제안·합의·철회·미해결과 서비스의 Decision State를 어떤 필드와 규칙으로 구별할까? 원문 출처 없는 AI 요약을 허용하는 상황에서 요약·직접 인용·추론의 의미와 허용 범위, 근거가 없는 rationale의 표현, 제출하지 않을 잡담의 경계를 정한다.

‘Redis를 검토하자’만 있는 경우, 결정은 있지만 이유가 없는 경우, 앞의 합의를 후반에 철회한 경우, 서로 다른 두 제안만 있는 경우를 대조한다. 사용자가 확정한 ‘검수 후보 제출’을 재논의하지 않고 후보의 표현·검증 계약을 구체화한다.

ADR-0014의 미합의 제안 제외 정책을 어떤 범위로 수정할지 결정하고, ADR-0019의 인간 확정 원칙을 유지한다. 기존 AI 출력의 decisionFound 의미도 이 결정에 맞춰 검토한다.

## Answer

### 후보의 의미와 제출 경계

Decision Candidate는 입력 대화에서 발견한 선택·변경·실행 제안 또는 합의의 검수 단위다. 합의 없는 제안도 제출한다. 문제 보고·질문·일반 정보 공유만 있으면 검수 후보로 제출하지 않고 논리 그래프의 맥락으로 보존한다.

모든 후보는 사람의 검수 전까지 Draft다. 대화에서 관측한 제안·합의·철회·불명확은 검수 상태와 별도로 표현한다. 합의가 관측되어도 자동 확정하지 않으며, 철회가 관측되어도 자동 Rejected 처리하지 않는다. 이러한 관측은 AI의 분석 결과이지 인간 검수 결과가 아니다.

### 요약과 근거

내용은 AI 요약으로 표현한다. 개별 원문 메시지 ID 연결과 직접 인용은 필수 조건이 아니며, 원문 일치 검사나 메시지별 출처 부재 때문에 요약 후보를 거부하지 않는다. AI가 작성한 문장은 요약으로 취급하고 실제 발언의 직접 인용으로 표현하지 않는다.

요약은 이번 입력 대화의 내용을 대상으로 한다. 입력 대화에 이유가 없으면 Rationale은 ‘근거 미언급’의 의미로 보존한다. 입력에 없는 이유를 AI가 사실로 추가하거나 추정 근거를 별도 생성하지 않는다. 구체적인 null/텍스트/메타데이터 표현은 논리 그래프 계약에서 정한다.

### 후보 묶음과 시간 흐름

같은 선택에 대한 경쟁 대안은 후보 하나로 묶는다. 독립적으로 실행할 수 있는 다른 결정은 별도 후보로 나눈다. Topic이 같다는 이유만으로 모든 결정을 합치지 않는다.

같은 선택의 제안·합의·철회 흐름은 같은 후보의 이력에 남기고, 현재 관측 결과를 함께 표시한다. 참여자의 의견이 충돌하거나 순서만으로 결론을 단정할 수 없다면 합의를 만들어내지 않고 불명확으로 표현한다. 세부 이벤트·관계 구조는 그래프 계약에서 결정한다.

### 합의한 사례

| 입력 | 처리 |
| --- | --- |
| Redis를 검토하자 | 제안이 관측된 후보, Draft |
| Redis로 가자 / 동의 | 합의가 관측된 후보, Draft |
| Redis로 가자, 이유는 없음 | 후보 제출, 근거 미언급 |
| Redis를 쓰자 / Memcached가 낫다 | 같은 선택의 후보 하나, 경쟁 대안 보존 |
| Redis로 가자 / Redis는 취소하자 | 후보 하나에 시간 흐름 보존, 철회 관측, Draft |
| 로그인이 느려 | 문제 맥락만 보존 |
| 로그인 캐시를 넣어보자 | 실행 제안 후보, Draft |

### 기존 정책과 다음 계약

ADR-0014의 미합의 제안을 false positive로 제외하는 기준은 이 설계에서 대체한다. 합의 검증은 제출 여부의 필수 조건이 아니라 대화 관측 결과를 구별하는 역할이다. ADR-0019의 인간 확정·Supersede 원칙은 유지한다.

현재 AI 출력의 decisionFound를 ‘합의된 결정 존재’로 사용하면 이 의미와 맞지 않는다. 구현 명세에서는 ‘검수할 후보 존재’를 표현하고 관측 결과를 별도로 전달해야 한다. 구체적인 필드 이름과 기존 출력 계약의 이행은 후속 그래프·저장 계약에서 정한다. 이 티켓 해결은 코드 구현 완료를 뜻하지 않는다.
