# 채널 분석 안정성 및 NVIDIA 호출 예산

Status: ready-for-agent

## Problem Statement

Bot 채널 스캔은 메시지를 수집했으나 AI 그래프의 구조·의미 검증 실패와 호출 시간 초과로 Decision Candidate를 게시하지 못했다. 사용자에게는 일반적인 재분석 안내만 보여 원인을 구분하기 어려웠다. 프롬프트 규칙을 개선할 때 저장된 분석이 이전 프롬프트 버전으로 재개될 수 있어야 한다. 현재 운영 NVIDIA 계정에는 분당 40회 호출 제한이 있어 여러 분석 세션과 BE 프로세스의 호출을 합쳐 이 한도를 지켜야 한다.

## Solution

분석 단계와 실패 종류를 사용자와 운영자가 확인할 수 있게 하고, 그래프 생성·수정 규칙을 서버 검증과 일치시킨다. 실패한 보관 입력의 명시적 재분석 경로를 제공한다. 저장된 분석은 생성 당시의 프롬프트 버전으로 계속 실행하고, 새 분석에만 새 프롬프트를 적용한다. NVIDIA 호출은 모든 BE 프로세스와 분석 단계가 공유하는 분당 40회 예산 안에서 예약·실행한다. 호출 예산 대기는 분석 실패나 유료 생성 시도로 오인하지 않는다.

## User Stories

1. 채널 분석 사용자로서 정상적인 후보 0건과 분석 실패를 구분하고 싶다. 그래야 결과를 신뢰할 수 있다.
2. 채널 분석 사용자로서 실패 단계와 복구 방법을 알고 싶다. 그래야 다시 시도할지 새 분석을 시작할지 결정할 수 있다.
3. 운영자로서 시간 초과, Provider 오류, 구조 오류와 의미 오류를 구분하고 싶다. 그래야 원인을 추적할 수 있다.
4. 운영자로서 요청 ID로 Bot 수집부터 BE 분석·게시까지 추적하고 싶다. 그래야 장애 지점을 찾을 수 있다.
5. 유지보수자로서 그래프 생성 지침이 서버 검증 규칙을 반영하기를 원한다. 그래야 수정 후에도 잘못된 연결과 상태값이 줄어든다.
6. 유지보수자로서 의미 검증 오류가 관련 노드·연결과 함께 수정 단계로 전달되기를 원한다. 그래야 정상 데이터를 보존하며 오류를 고칠 수 있다.
7. 채널 분석 사용자로서 실패한 분석의 보관 입력을 명시적으로 재분석하고 싶다. 그래야 Discord 메시지를 다시 수집하지 않아도 된다.
8. 검수자로서 재분석이 기존 Review Queue 결과를 덮어쓰지 않기를 원한다. 그래야 승인·거절 기록이 보존된다.
9. 운영자로서 진행 중이던 분석이 배포 뒤에도 원래 프롬프트 버전으로 이어지기를 원한다. 그래야 검증 규칙이 중간에 바뀌지 않는다.
10. 운영자로서 새 프롬프트 버전은 새 분석에만 적용되기를 원한다. 그래야 기존 체크포인트의 의미를 보존한다.
11. 운영자로서 NVIDIA 요청이 계정의 분당 40회 한도를 넘지 않기를 원한다. 그래야 여러 채널 스캔이 동시에 발생해도 할당량 오류를 피할 수 있다.
12. 운영자로서 대기 중인 호출이 취소되면 예산을 불필요하게 소모하지 않기를 원한다. 그래야 다른 요청이 진행할 수 있다.
13. 운영자로서 호출 한도 대기 시간과 실제 Provider 호출 시간을 따로 보고 싶다. 그래야 시간 초과 원인을 구분할 수 있다.
14. 운영자로서 AGY와 NVIDIA의 독립적인 호출 정책을 유지하고 싶다. 그래야 NVIDIA 한도가 AGY 분석을 막지 않는다.
15. 운영자로서 Loki에서 AI 호출 성공률과 분석 요청 완료율을 별도로 보고 싶다. 그래야 생성은 성공했지만 검증에서 실패한 요청을 놓치지 않는다.

## Implementation Decisions

- 운영 NVIDIA 계정의 분당 40회 제한은 사용자가 제공한 현재 배포 제약이다. 모든 배포·계정의 일반적인 NVIDIA 한도로 가정하지 않는다. 설정값은 해당 계정의 한도 이하로 지정할 수 있고 기본 운영값은 분당 40회다.
- 한도는 추출·검증·수정의 NVIDIA 네트워크 생성 요청 전체에 적용한다. BE 프로세스별 로컬 카운터만으로는 다중 프로세스 한도를 보장할 수 없으므로 기존 공유 스케줄러 또는 같은 영속 저장소를 사용해 원자적으로 예약한다.
- 60초 구간의 경계, 예약 시점, 취소·시간 초과 시 예약의 회수 여부를 명시한다. 실제 전송된 요청은 결과와 관계없이 호출로 계산하고, 전송 전 취소된 대기는 호출로 계산하지 않는다.
- Provider가 429 또는 Retry-After를 반환하면 지정된 대기 시간을 존중하고 기존 durable queue의 재시도 정책과 연결한다. 몰래 다른 Provider로 전환하거나 숨은 생성 재시도를 추가하지 않는다.
- 호출 예산 대기는 세션 예산·호출 제한 시간·취소와 함께 설계한다. 허용된 예산 안에 실행할 수 없으면 명시적인 용량/대기 상태로 보존한다.
- 분석 알고리즘은 기존 공통 실행 계약을 사용한다. Provider별 호출 한도와 HTTP·CLI 전송 차이는 조립 및 Provider 경계에 둔다.
- 프롬프트 버전별 지침을 보존한다. 새 분석은 새 버전으로 시작하고, 저장된 분석은 기록된 버전의 추출·검증·수정 지침으로 재개한다. 알 수 없는 버전은 명시적으로 실패한다.
- 그래프 구조·의미 검증과 요청 단위 원자적 후보 게시 정책을 유지한다. 기존 Review Queue 결과와 Evidence Hash를 존중한다.
- 사용자에게 제공하는 오류는 안전한 분류와 행동 안내만 포함한다. 원문, 자격증명 및 Provider 전체 응답을 노출하지 않는다.
- Bot·BE의 요청 ID와 최종 분석 결과를 로그에서 연결한다. 요청 ID는 Loki의 고카디널리티 라벨로 만들지 않는다. AI 호출 성공과 최종 분석 성공을 별도 지표로 표시한다.

## Testing Decisions

- 좋은 테스트는 내부 카운터나 파일 구조보다 실제 요청 전송 수, 순서, 취소, 결과, 재개 상태 및 사용자 조회 결과를 검증한다.
- 기존 분석 실행 인터페이스에서 저장·재시작·실패·게시를 확인한다. 기존 Provider 인터페이스에서 AGY/NVIDIA 요청 계약과 프롬프트 버전을 확인한다.
- 다중 BE 인스턴스를 같은 저장소에 연결해 60초 동안 NVIDIA 호출 40회를 넘지 않음을 가짜 시계와 전송 구현으로 결정적으로 검증한다. AGY 호출은 별도로 진행됨을 확인한다.
- 대기 취소, 시간 초과, 429/Retry-After, 프로세스 재시작, 분 경계와 공정한 순서를 검증한다. 실제 NVIDIA API 호출은 자동 테스트 필수 조건이 아니다.
- 기존 분석 체크포인트의 프롬프트 버전이 배포 후에도 유지되고 새 요청만 새 버전을 쓰는지 확인한다.
- 실제 장애에서 관측된 잘못된 연결 대상, 허용되지 않은 상태값, 수정 후 검증 실패와 20초 시간 초과를 회귀 사례로 사용한다.
- 검증은 변경 범위의 BE·Bot·Shared 테스트와 타입 검사로 한정하며 FE 전체 테스트를 실행하지 않는다.

## Out of Scope

- 자동 Provider 전환, 무제한 수정 시도, 검증 실패 그래프의 부분 게시.
- 운영 Discord 데이터를 자동으로 재분석하거나 기존 검수 결과를 변경하는 작업.
- 계정 한도를 실제 NVIDIA 계정에서 검증하지 않고 40회보다 높게 조정하는 작업.

## Further Notes

2026-11-08 스캔에서 메시지 33개를 수집했으나 구조·의미 검증 실패와 앞선 20초 시간 초과가 관측되었다. 이 명세는 승인된 분석 안정성 티켓 01–05와 후속 로깅·Loki 개선을 묶어 설명한다. NVIDIA 분당 40회는 사용자 제공 운영 제약이며 공식 계정 할당량 조회로 확인된 수치는 아니다.
