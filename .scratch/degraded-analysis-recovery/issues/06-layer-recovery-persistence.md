# 06: 세션 복구의 DB 접근을 저장소로 모으고 정책을 서비스로 옮김

**What to build:** ADR-0021의 계층 경계에 맞춰, 세션 복구 기록(`AnalysisSessionRecovery`)에 대한 쿼리와 트랜잭션은 저장소가 실행하고, 재시도 지연·입력 보관 기한·수동 재분석 여부 같은 정책은 서비스가 정한다. 동작은 바꾸지 않는다.

**Blocked by:** 03: 건너뛴 세션의 자동·수동 복구, 04: 실패 입력의 보관 기한

**Status:** done

- [x] `AnalysisSessionRecoveryRepository`를 만들고, `analysis-session-recovery.ts`, `analysis-query.service.ts`, `sync-job.service.ts`에서 복구 테이블을 직접 다루는 Prisma 호출을 모두 이 저장소로 옮긴다.
- [x] `candidate-publication.repository.ts`는 복구 기록을 만들 때 첫 재시도 지연(1분), 보관 기한(30일), 수동 재분석 여부를 스스로 정하지 않고 서비스가 계산한 값을 받는다.
- [x] 재시도 지연(1분·5분), 최대 시도 수, 보관 기한을 이름 붙은 정책 상수로 한곳에 둔다.
- [x] 큐 서비스가 호출할 때마다 복구 서비스를 새로 만들지 않고 생성자에서 한 번 만든다.
- [x] 기존 복구·건너뜀·만료 테스트가 수정 없이 통과한다.

## Comments

**2026-11-19:** `ai-call-reliability` 구현 뒤 Standards 리뷰에서 나온 ADR-0021 위반(서비스의 직접 쿼리, 저장소의 정책 결정)을 정리한다.

**2026-11-19 구현:** 동작을 바꾸지 않는 리팩터링이라 새 테스트 없이 기존 테스트로 확인했다. 테스트 파일은 고치지 않았고 BE 248건, Bot 55건, 타입 검사가 통과했다. 리뷰에서 확인했듯 옮긴 where 절과 상태 우선순위는 HEAD와 같다. 남겨 둔 판단 사항:
- 보관 만료 시각은 최초 요청 생성 시점이 트랜잭션 안에서만 확정되므로, 정책 기간은 서비스가 넘기고 더하기는 저장소가 한다.
- `purgeExpiredInputs`가 요청·영수증·세션 입력까지 함께 지우는 것은 한 트랜잭션이어야 해서 이 저장소에 두었다.
- Prisma가 문자열로 돌려주는 `state`·`failureKind` 필드는 저장소 경계에서 좁히지 않았다.
