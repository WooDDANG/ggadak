# 전수검사 부하 제어 설계

Status: ready-for-agent

## 합의한 방향

- 최신 합의: BE가 현재 전송할 채널을 지정하고 Bot이 고정 검사 범위를 구간별 순차 전달한다. BE는 채널 전체의 영속 수신·완전성 확인 후 자동 분석한다. A 수신 완료와 수신 여유를 기준으로 B를 지시할 수 있어 A 분석과 B 수집·전달을 겹친다. 앞서 정한 'A 분석 종료 후 B 전송'은 이 합의로 대체한다.
- 큐 소유권: Bot은 미확인 전달을 보존하고 BE 영속 수신 확인 후 전달 완료 처리한다. BE는 입력과 처리 의도를 보존하고 분석 대기·실행·재시도를 책임진다. Bot의 결과 반영은 데이터 전달과 독립적으로 수행한다. 사용자가 이 구분까지 티켓에 추가하도록 명시했다.
- 복구 구분: 원본 데이터 누락은 Bot에 재전송 요청하고, AI 분석 실패는 BE에 보관된 입력으로 재시도한다. 분석 실패만으로 Discord 대화를 다시 수집하지 않는다.
- 전수검사 완료 속도보다 로그인·대시보드 응답성을 우선한다. 부하가 높으면 전수검사를 감속하거나 대기시키며, 완료한 Scan Range와 Channel Checkpoint를 보존해 재시작 후 이어간다.
- 다음 Analysis Request를 선택할 때 실시간·수동 요청을 전수검사보다 우선한다. 실행 중인 분석은 마무리하고 전수검사의 진행 기회도 보장한다.
- 사용자 확인: 첫 인터뷰의 Q1·Q2에 “예”. 구체적인 자원 한도와 운영 정책은 미확정이며 구현 승인을 뜻하지 않는다.
- Q4 합의: 요청 제한·일시 장애로 실패한 Analysis Request는 동일한 식별자를 유지해 재시도 간격을 늘린다. 재시도 한도를 넘기면 실패로 보존하고 웹에서 수동 재시도한다. 완료한 범위는 다시 검사하지 않고 실패 범위를 완료로 표시하지 않는다. 사용자는 재시도의 의미를 확인한 뒤 “예”로 답했다.
- Q3·Q5 합의: 전수검사에서는 개별 처리 반응을 생략하고 실행자에게 시작·종료 요약, 웹에 상세 진행 상태를 제공한다. 실시간·수동 분석의 표시는 유지한다. BE·AI 공통 과부하에서는 새 전수검사 요청 전체를 대기시키며, 특정 채널의 권한 오류는 해당 채널에 한정한다. 진행 중 요청은 강제로 취소하지 않는다.

## 확인한 사실

- 전수검사의 채널·Scan Range 순회 자체는 순차적이다. 채널 단위 스케줄러는 있으나 다른 진입점과 공유하는 전체 분석 동시 실행 한도는 별도로 검토해야 한다.
- `apps/bot/src/services/backend-api.service.ts`의 `reconcileDeliveryReactions`는 완료되지 않은 보관 요청을 반복 순회하며 반응 정리를 예약한다.
- 같은 파일의 `recoverScanCheckpoints`는 변경 여부와 무관하게 보관된 Scan Range의 채널별 체크포인트를 다시 조회한다.
- 같은 파일의 `synchronizeDeliveryStatus`는 완료 항목을 포함한 전체 상태를 전송하고, `apps/be/src/services/analysis-delivery.service.ts`는 매 동기화에서 항목별 조회·upsert를 실행한다.
- 과거 로그의 높은 요청 수는 현재 시점의 병목을 확정하는 근거로 사용하지 않는다. Discord 채팅 전송, 반응 정리 API, BE 분석·복구·상태 동기화를 구분한다.
- ADR-0020의 요청 식별자 유지, 실패 보존, 연속 완료 범위만 체크포인트로 인정하는 원칙을 유지한다.

## 발행 상태

- 사용자가 데이터 정리 티켓 추가와 기존 수용 기준 보강을 승인해 10개 이슈를 발행했다. 기준 문서는 [구현안](./spec.md)이며 개별 이슈는 issues 디렉터리를 따른다. SSE·WebSocket 도입은 확정하지 않았다.
- 01 수신 확인 → 02 BE 분석 큐 → 03 선택 복구 → 04 전달·분석 병행 → 05 처리량 제어. 06 상태 변경분과 08 체크포인트는 독립 시작 가능하다. 07 결과 독립 처리는 02·06, 09 자료 정리는 05·07·08, 10 통합 검증은 09에 의존한다.

## 다음 단계

발행한 이슈의 선행 조건이 없는 01·06·08부터 착수할 수 있다. 현재 요청 범위인 티켓 발행을 완료했으며 코드 구현은 수행하지 않았다.

## 추가 확정

- 사용자는 재시도 한도를 넘긴 채널 A를 실패로 보존하고 채널 B로 진행하는 정책에 “예”로 답했다. A의 미완료 구간은 성공 처리하지 않고 웹에서 복구한다.
- 현재 요청은 to-tickets이며 코드 구현은 수행하지 않는다. 최종 보강 승인 후 10개의 개별 로컬 이슈로 발행했다.
- 추가 검토 결과를 승인받아 채널 수신 용량 교착 방지·초기 기본 제한·운영 병목 지표·기존 작업 전환 검증을 보강했고, 완료 자료 정리와 복구 기록 보존을 별도 이슈로 추가했다.

## 조사 보충

- 복구 루프 위치는 `apps/bot/src/bot/client.ts`다. 매초 체크포인트 복구가 두 번 호출되고 반응 정리도 반복된다.
- 과거 2026-10-16 10:29~10:31 로그는 분당 약 770개 요청 중 체크포인트 조회 720개를 기록했다. 조사 시점의 최근 23:56 로그는 분당 25개 요청이며 체크포인트 폭주는 보이지 않았다. 과거 빈도는 중복 Bot 실행 가능성을 시사하지만 이를 확정하지 않는다.
- 상태 동기화 주기를 조절할 경우 BE의 15초 생존 판정 계약을 함께 검토한다.
