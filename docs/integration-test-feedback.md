# 통합 테스트 피드백 및 화면 예외 처리 현황 (Integration Test Feedback)

이 문서는 FE(웹 프론트엔드) ↔ BE(API 백엔드) ↔ Discord/SQLite 간 통합 테스트 과정에서 발생하는 런타임 에러, 비동기 경합, 네트워크/외부 의존성 장애 및 이에 따른 화면(UI) 예외 처리 요구사항을 기록하고 추적하는 문서입니다.

---

## 1. 테스트 환경 개요

- **테스트 브랜치**: `fix/permission-recovery-loop` (또는 활성 통합 브랜치)
- **실행 환경**:
  - FE: Vite 개발 서버 (`localhost:5173` / `localhost:3000`)
  - BE: Express + TSOA API 서버 (`localhost:3001`)
  - DB: 로컬 SQLite (`apps/be/decisions.sqlite` 또는 테스트 격리 DB)
- **통합 검증 커맨드**:
  - E2E 브라우저 회귀: `npm run test:e2e -- tests/e2e/frontend-selection.test.ts`
  - FE 단위/통합 테스트: `npm run test --workspace=apps/frontend-main`
  - 전체 빌드 및 테스트: `npm run typecheck && npm test`

## 3. 중점 에러 상세 및 화면 예외 처리 지침

### IT-01: 권한 확인 실패 시의 자동 복구 무한 순환 (Permission Recovery Loop)

#### 1) 발생 증상 및 원인

- **로그**: `[ERROR] [ERROR-HANDLER]: Error: Discord permissions could not be verified; retry shortly`
- **원인**: 백엔드 `AuthService.checkGuildAccess`에서 Discord 권한 검증에 일시 실패(또는 레이트 리밋)할 때, 프론트엔드가 권한 오류를 감지하고 서버 목록 재조회 및 복구 로직을 트리거함.
- 서버 목록 조회는 200 OK로 성공하지만 직후 데이터 요청(`/api/v1/dashboard`, `/api/v1/decisions`)이 다시 실패하면서 짧은 시간(500ms) 동안 수십 회의 복구 루프가 반복 발생.

#### 2) 화면(UI) 예외 처리 요구사항

- [ ] **자동 복구 횟수 제한 (Single Attempt Bound)**:
  - 동일 서버/계정 범위에서 연속 권한 에러 발생 시 자동 복구(토큰 갱신 또는 서버 목록 재확인)는 **최대 1회**로 제한.
- [ ] **안정적인 에러 화면 고정**:
  - 복구 실패 시 화면을 로그인 화면이나 초기 화면으로 튕겨내지 않고, 현재 서버 컨텍스트를 유지한 채 **안정적인 오류 안내 화면**에 머무름.
- [ ] **수동 재시도 버튼 제공**:
  - `[다시 시도]` 버튼을 제공하여 사용자가 의도한 시점에만 단발성으로 재요청하도록 유도.
- [ ] **이벤트 트리거 억제**:
  - 지속 실패 상태에서는 윈도우 `focus`, `online`, 또는 지연된 비동기 응답이 도착하더라도 자동 복구 사이클을 재시작하지 않음.
- [ ] **편집 초안(Draft) 및 세션 보호**:
  - 에러가 발생해도 사용자가 작성 중이던 의사결정 카드 편집 초안(Local Storage / State)과 로그인 쿠키 세션을 유실 없이 유지.

### IT-02: 서버 접근 권한 불일치 및 데이터 조회 예외

#### 1) 발생 증상

- 사용자가 속한 디스코드 서버 목록은 정상 렌더링되나, 특정 서버 선택 시 카드 데이터나 대시보드 API가 403 Forbidden 또는 503 Service Unavailable을 반환.

#### 2) 화면(UI) 예외 처리 요구사항

- [ ] **스켈레톤 및 무한 로딩 방지**:
  - API 실패 시 무한 스피너를 표시하지 않고 최대 타임아웃 이후 에러 뷰로 즉시 전환.
- [ ] **부분 실패(Partial Failure) 분리**:
  - 상단 내비게이션/서버 선택기는 활성 상태를 유지하여 사용자가 다른 정상 서버로 즉시 이동할 수 있도록 허용.
- [ ] **폴링 정지**:
  - 대시보드의 2초 주기 자동 폴링(`dashboard.service`)은 에러 응답 수신 즉시 일시 정지하여 불필요한 백엔드 트래픽 차단.

---

### IT-03: Discord API 외부 장애 및 Rate Limit (429 / 5xx)

#### 1) 발생 증상

- Discord 게이트웨이나 REST API 지연으로 인해 BE가 지연 응답하거나 429 상태 코드가 프론트로 전달됨.

#### 2) 화면(UI) 예외 처리 요구사항

- [ ] **친절한 오류 메시지 매핑**:
  - 기술적인 `503 Service Unavailable` 또는 `Discord permissions could not be verified` 문자열 대신 "디스코드 연동 권한을 확인하는 중입니다. 잠시 후 다시 시도해주세요."와 같은 사용자 친화적 메시지 출력.
- [ ] **버튼 디바운싱 및 비활성화**:
  - 새로고침이나 재시도 버튼 클릭 시 3~5초간 버튼을 비활성화(`disabled`)하여 연속 클릭 방지.

---

### IT-04: 봇 미설치 또는 채널 권한 부재 서버

#### 1) 발생 증상

- 사용자는 관리자 권한을 가졌으나, 디스코드 봇이 해당 서버에 설치되어 있지 않거나 모니터링 채널 권한(ViewChannel, ReadMessageHistory)이 없는 경우.

#### 2) 화면(UI) 예외 처리 요구사항

- [ ] **엠프티 스테이트(Empty State) 분기**:
  - "의사결정이 없습니다"와 "봇이 서버에 설치되지 않았습니다"를 명확히 구분하여 안내.
- [ ] **봇 초대 링크 제공**:
  - 미설치 서버 감지 시 `[디스코드 봇 초대하기]` 외부 링크 버튼을 눈에 띄게 배치.

---

### IT-05: 세션 만료(401) 및 토큰 갱신 경합

#### 1) 발생 증상

- 브라우저를 오래 켜두었거나 토큰 수명이 다했을 때 여러 API가 동시 다발적으로 401을 수신하여 다중 리프레시 요청이 발생하는 현상.

#### 2) 화면(UI) 예외 처리 요구사항

- [ ] **Axios 인터셉터 프로미스 락**:
  - 토큰 갱신 중 들어오는 추가 401 요청들은 큐에 대기시켰다가 갱신된 토큰으로 일괄 재시도.
- [ ] **강제 로그아웃 시 초안 보존**:
  - 갱신이 최종 실패하여 로그인 화면으로 리다이렉트되어도 작성 중인 폼 내용은 로컬 스토리지에 유지하여 재로그인 후 복구 지원.

---

### IT-06: E2E 브라우저 테스트 `screen condition timed out` (화면 조건 감지 타임아웃)

#### 1) 발생 증상 및 원인

- **테스트**: `tests/e2e/frontend-selection.test.ts > real frontend OAuth, cookie restore, server installation events and draft recovery cross the actual backend`
- **스택 트레이스**:
  ```text
  Error: screen condition timed out
   ❯ Module.runFrontendJourney tests/e2e/support/frontend-browser.ts:274:27
   ❯ tests/e2e/frontend-selection.test.ts:7:20
  ```
- **원인**:
  - 권한 복구 순환 차단 로직(FE `useAuth.jsx`, `client.js`) 수정 작업 도중, 서버 인벤토리 변경/권한 확인 불가 상태에서 기대하는 화면 엘리먼트(`button('다시 시도')` 또는 `#serverSelect`) 노출 시점과 테스트 러너의 조건 검사 타이머(wait) 간 불일치가 발생.
  - 비동기 상태 전환 도중 컴포넌트 렌더링이 지연되거나 중간 렌더 사이클에서 에러 화면이 기대한 DOM 셀렉터 형태로 노출되지 않아 타임아웃 발생.

#### 2) 화면(UI) 예외 처리 요구사항

- [ ] **결정적 렌더링 상태 보장**:
  - 권한 확인 불가(`unverified`/`error`) 상태로 전이될 때, 로딩 상태가 풀리고 즉시 에러 뷰 및 `[다시 시도]` 버튼이 안정적으로 DOM 트리에 마운트되도록 보장.
- [ ] **과도기(Transition) 스피너/플레이스홀더 정돈**:
  - 네트워크 지연 시 불필요한 DOM 플리커링(사라졌다 다시 나타남)을 억제하고 일관된 에러 컨테이너 유지.
- [ ] **접근성 및 테스트 셀렉터 일관성**:
  - `data-testid` 또는 고유 버튼 텍스트를 명확히 유지하여 사용자 스크린리더 및 E2E 브라우저 러너가 안정적으로 화면 전이를 감지할 수 있도록 처리.
