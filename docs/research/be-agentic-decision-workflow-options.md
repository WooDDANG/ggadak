# BE Agentic 의사결정 분석 워크플로우 선택지 조사

조사일: 2026-10-13. 상태: 설계 판단을 위한 사실 조사이며 알고리즘·모델·프레임워크 채택 문서가 아니다.

## 범위와 결론

입력 Discord 대화 안에서 합의된 결정과 미합의 제안을 검수 후보로 추출하고 논리 그래프를 만든다. 개별 원문 출처가 없는 AI 요약도 허용한다. 사람이 최종 확정하며 과거 결정 조회, FE 좌표·렌더링, 앱 구현은 제외한다.

**고정된 TypeScript 단계와 조건부 수정만으로도 agentic 워크플로우를 표현할 수 있다.** 동적 supervisor나 Python 도입이 필수라는 근거는 없다. Anthropic은 미리 정한 코드 경로를 workflow, 모델이 경로·도구를 정하는 구조를 agent로 구분하며 단순한 방식부터 측정할 것을 권한다. evaluator-optimizer는 명확한 평가 기준과 수정 효과가 있을 때 적합하다. 이 구분은 패턴 설명이며 까닭의 품질을 보장하지 않는다. [Anthropic 공식 패턴 설명](https://www.anthropic.com/engineering/building-effective-agents)

## 비교할 수 있는 구성

| 선택지                      | 역할과 실행 경로                                                       | 이 프로젝트에서 확인할 점                                                                |
| --------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 단일 추출 + 코드 검증       | 대화 → 후보·그래프 한 번 생성 → 구조 검사 → 검수 제출                  | 비교 기준으로 쓸 최소 구성. 암묵적 근거·미합의 제안 누락을 사례로 측정                   |
| 추출 + critic + 제한된 수정 | 대화·후보를 별도 critic이 평가 → 오류 목록 → 필요할 때만 수정 → 재검사 | critic이 정확한 오류를 찾는지, 수정이 누락·환각을 늘리지 않는지 측정                     |
| 노드·관계 역할 분리         | 노드 추출 → 식별자가 정해진 노드 목록으로 관계 추출 → 병합 검증        | 병렬 독립 생성 시 식별자·의미 불일치 처리 필요. 직렬이면 지연 증가 가능                  |
| 동적 orchestrator           | 모델이 작업을 분할하고 worker를 선택·통합                              | 대화 크기·복잡도에 따른 분할 이득이 있을 때 검토. 단계·호출 수가 가변이라 예산 추적 필요 |

표는 조사자의 비교 틀이며 제품 결정이 아니다. TypeScript LangGraph 공식 예제에는 chaining, parallelization, orchestrator-workers, evaluator-optimizer가 있다. 따라서 Python 예제의 `TypedDict`·Pydantic·`@step`을 BE 설계의 전제로 둘 이유는 없다. 프레임워크 없이 현재 Service/Adapter 경계에 단계 함수를 두는 방식도 별도 선택지다. 설치된 `ai` 3.x와 `zod` 3.x에 최신 문서 예제를 바로 붙일 수 있다는 뜻은 아니다. [LangGraph JavaScript 패턴](https://docs.langchain.com/oss/javascript/langgraph/workflows-agents), [현재 BE 의존성](../../apps/be/package.json)

## 구조화 출력이 보장하는 범위

OpenAI Structured Outputs는 응답 스키마 준수를 지원하지만, 공식 문서는 내용 오류가 남을 수 있다고 명시한다. refusal은 요청한 스키마와 다른 응답일 수 있고 출력 제한에 의한 미완료도 별도로 처리해야 한다. 따라서 **스키마 통과 = 결정 사실성·합의·논리 관계 정확성**으로 처리하면 안 된다. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

Gemini도 JSON Schema의 일부를 지원하며 앱의 값 검증과 의미 오류 처리를 요구한다. 모델·API·스키마 복잡도에 따라 지원 범위를 확인해야 한다. 현재 문서의 요청 형태가 기존 Adapter가 사용하는 API와 동일하다고 가정하지 않는다. [Gemini 구조화 출력과 한계](https://ai.google.dev/gemini-api/docs/structured-output)

출처 없는 요약을 허용하는 제품 결정은 메시지별 citation을 필수로 하지 않는다는 뜻이다. 입력에 없는 합의·담당자·기한을 사실로 만들어도 된다는 뜻은 아니다. 요약, 직접 인용, AI가 추론한 관계를 어떻게 표시·검증할지는 인간 결정 티켓에서 정한다.

## 검증과 종료를 분리하기

LangGraph `recursionLimit`은 그래프의 super-step 수를 제한하고 초과 시 오류를 낸다. critic 수정 횟수나 총 provider 호출 수와 같은 값이 아니다. 공식 문서도 명시적 종료 조건을 만들고 제한 오류를 안전망으로 처리하라고 안내한다. 병렬 worker, provider 재시도, critic 수정 예산을 각각 구분해야 한다. [LangGraph 종료 조건과 recursion limit](https://docs.langchain.com/oss/javascript/langgraph/graph-api#recursion-limit)

후속 설계에서 정할 종료 조건 후보는 구조 검증 성공, 수정 횟수 소진, 전체 호출·토큰·시간 예산 소진, 수정 전후 변화 없음, 취소·소유권 상실이다. 성공·후보 없음·검증 미완료·provider 실패를 같은 빈 배열로 합치지 않는 것도 계약 결정 대상이다. 이는 프로젝트에 대한 제안이며 공식 문서가 정한 기본값이 아니다.

네트워크 실패 후 같은 요청 재전송과, critic 피드백을 넣어 새 결과 생성은 서로 다른 동작이다. 기존 AnalysisRequest 멱등성과 사람이 확정하는 경계를 유지하는 방법은 앱의 저장·복구 계약과 함께 결정해야 한다. 프레임워크 checkpoint만으로 앱 DB 중복 저장 방지가 해결됐다고 판단할 수 없다.

## 논리 그래프의 검사 층

JSON Schema는 배열의 항목 형태·길이·항목 전체의 중복 여부 같은 제약을 표현한다. `uniqueItems`가 각 노드의 `id` 필드만 유일하게 만들거나, edge의 `sourceId`가 다른 배열에 존재하도록 일반적으로 연결해 주는 것은 아니다. [JSON Schema 배열 제약](https://json-schema.org/understanding-json-schema/reference/array)

| 층   | 코드로 검사할 수 있는 예                            | 별도 의미 평가가 필요한 예              |
| ---- | --------------------------------------------------- | --------------------------------------- |
| 형태 | 노드·관계 타입, 비어 있지 않은 텍스트, 크기 제한    | 요약이 대화 의미를 보존하는가           |
| 참조 | ID 유일성, 양 끝 노드 존재, 허용한 타입 조합        | 해당 근거가 실제로 그 대안을 지지하는가 |
| 정책 | 금지한 자기 연결·관계 중복, 허용한 인용의 원문 일치 | 대화 후반의 발언이 합의를 뒤집었는가    |
| 제출 | 검수 후보와 연결된 그래프, 입력 범위 식별           | 미합의 제안을 확정 사실처럼 표현했는가  |

전체 그래프에 DAG 제약을 적용하는 것은 아직 결정하면 안 된다. 논리 그래프의 `conflicts_with`와 실행 워크플로우의 순환은 다른 관계다. 어떤 관계에 방향성·대칭성·비순환성을 요구할지는 그래프 계약에서 정한다. 위 검증 항목은 구현된 기능이 아니라 계약 검토 항목이다.

## 출발 연구 문서의 재확인 결과

| 기존 주장                                       | 확인 결과                                                                                                    |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| evaluator-optimizer 패턴                        | 공식 패턴 설명이 있음. 그러나 까닭의 성능 향상은 검증하지 않음                                               |
| 최대 3회 자가 치유                              | 조사한 공식 패턴 설명이 정한 공통 상수가 아님. 제품 예산 후보                                                |
| Consensus Score ≥ 0.85로 종료                   | 해당 임계치의 근거·보정 데이터가 없음. 합의 없는 제안도 제출하는 요구와 별도 논의 필요                       |
| JSON 스키마로 100% 구문 오류 없는 무결점 그래프 | refusal·미완료 예외와 의미·참조 오류를 구분해야 하므로 절대적 표현은 부정확                                  |
| TextTiling으로 임베딩 대화 경계 확정            | 원 논문은 문서 하위 주제 분할의 근거. 한국어 Discord 임베딩 변형의 성능까지 뒷받침하지 않음                  |
| Kummerfeld 기반으로 스레드 복원                 | 원 논문은 대화 disentanglement 데이터·모델의 근거. 현재 코드나 한국어 데이터에서 채택·검증했다는 근거가 아님 |
| LangGraph가 필수/업계 표준                      | 공식 API 존재와 기술 채택의 필수성은 별개. 현재 BE에 대한 비교 실험이 없음                                   |

TextTiling과 disentanglement의 적용 가능성은 출발점으로 남기며 이번 조사에서 독립 구현·실험하지 않았다. [Hearst 원 논문](https://aclanthology.org/J97-1003/), [Kummerfeld 등 원 논문](https://aclanthology.org/P19-1374/)

레이아웃 엔진의 유지보수 현황, Napkin 내부 Spark 알고리즘, Eraser 공개 저장소 주장 등 FE·벤더 내부 구현 내용은 이 티켓의 조사 범위 밖이며 검증된 설계 근거로 사용하지 않는다.

## 아직 결정할 질문

- 한 번에 후보·그래프를 생성할지, 후보와 관계를 나눌지, critic이 필요한 오류를 무엇으로 정의할지.
- 인용이 없는 요약과 추론 관계를 검수자에게 어떤 메타데이터로 구별할지.
- 제한 초과 시 유효한 일부 후보를 제출할지 전체 요청을 실패 보존할지.
- 한국어 대화 평가셋에서 제안 recall, 잘못된 합의 표현, 입력 밖 주장, 관계 정확도, 비용·지연을 어떤 기준으로 비교할지.

실제 provider 호출, 모델 정확도 평가, 프레임워크 설치, 앱 수정은 수행하지 않았다. 기존 연구의 수치나 스택 제안을 채택하는 대신 이 질문들을 설계 map에서 합의해야 한다.
